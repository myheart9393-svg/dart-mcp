# /dart-review $ARGUMENTS

`$ARGUMENTS`는 리뷰할 보고서 파일 경로다(`reports/....md`).

## 실행 방식: 반드시 서브에이전트

이 커맨드를 받은 쪽(작성자)은 **직접 리뷰하지 않는다.** Agent 툴(subagent_type `general-purpose`)로 리뷰어를 띄우고,
prompt에는 아래 한 단락**만** 넣는다. 작성 과정의 대화·메모·읽은 섹션 내용은 넣지 않는다(작성자가 자기 글을 검토하지 않기 위해).

```
너는 DART 분석 보고서의 독립 리뷰어다. 프로젝트 루트의 .claude/commands/dart-review.md 에서
"## 리뷰어 지침" 절을 읽고 그대로 수행하라. 리뷰 대상: <보고서 경로>.
dart MCP 툴(get_key_financials, get_disclosure_outline, get_disclosure_section, search_in_disclosure 등)을 써도 된다.
끝나면 리뷰 파일 경로, 항목별 PASS/FAIL, MCP 툴 호출 횟수(툴별), 읽은 글자 수를 짧게 답하라.
```

리뷰어가 끝나면 작성자는:
1. `<보고서명>.review.md`의 FAIL 항목을 하나씩 반영해 보고서를 고친다(리뷰가 틀렸다고 판단하면 고치지 않고 이유를 적는다).
2. 보고서 맨 끝(부록 뒤)에 `## 리뷰 반영 내역` 표를 추가한다: `| 리뷰 항목 | 위치 | 수정 전 | 수정 후 / 미반영 사유 |`.
3. **리뷰는 1회로 끝낸다.** 고친 뒤 다시 리뷰를 돌리지 않는다(비용 통제).
4. 채팅에 리뷰 PASS/FAIL 현황, 고친 항목, 툴 호출 횟수(작성/리뷰 분리)를 보고한다.

`/dart-review`를 사용자가 단독으로 부른 경우(이미 있는 보고서 점검)도 똑같이 서브에이전트로 리뷰하고, 반영은 사용자가 원할 때만 한다.

## 리뷰어 지침

너는 보고서 작성 과정을 모른다. 보고서 파일과 dart MCP만으로 판정한다. 보고서를 고치지 말고 리뷰 파일만 쓴다.

### 0. 준비
- 보고서를 Read로 한 번 읽는다. 머리말·출처 표기에서 rcept_no, corp_code(없으면 `find_company`), 사업연도, 연결/별도를 파악한다.
- 정규식 점검을 먼저 돌린다: `uv run python -m dart_mcp.report_lint <보고서 경로>` (Bash). 결과 JSON은 d·a 항목의 **후보**다.

### a. 출처 누락
- 숫자(금액·%·배·주·건)가 나오는 모든 문장·표에 `(rcept_no, section_id)` 또는 `(rcept_no, 재무API)` 출처가 있는지 본다.
  같은 단락 끝이나 표 바로 아래 한 번 붙인 출처는 그 단락·표 전체를 덮는 것으로 본다. "계산"이라고 밝힌 비율·배수는 계산 근거가 된 수치의 출처가 있으면 PASS.
- report_lint의 `number_without_citation_candidate`는 후보일 뿐이다. 읽어서 실제 누락만 FAIL로 적는다.

### b. 재무 표 API 대조
- 보고서의 재무 표(매출·영업이익·순이익·자산·부채·자본·현금흐름·비율)를 `get_key_financials`로 다시 받아 셀마다 대조한다
  (연간: reprt_code 11011, "최근 분기 동향" 표가 있으면 그 reprt_code·period_type으로).
- 단위 환산(원→백만원/억원/조원) 후 반올림 차이(마지막 자리 ±1)는 일치로 본다. 그 이상은 불일치 목록에 `표/행/연도/보고서 값/API 값`.
- 분기 표가 연간 값과 같은 표·같은 열에 섞여 있거나, 분기 prior를 "전년"이 아닌 다른 기간으로 적었으면 FAIL.

### c. 원문 인용 숫자 샘플 확인
- 출처가 `(rcept_no, section_id)`인(재무API가 아닌) 숫자 중 **5개**를 고른다. 고르는 방법: 후보를 문서 순서로 번호 매기고
  `uv run python -c "import random; random.seed(<보고서 파일 크기 바이트>); print(sorted(random.sample(range(1, N+1), 5)))"`로 뽑는다(재현 가능).
  후보가 5개 미만이면 전부.
- 각 숫자를 `search_in_disclosure(rcept_no, <숫자 또는 주변 키워드>)`로 위치를 찍고, 필요하면 `get_disclosure_section(..., offset, max_chars≤4000)`으로 그 부근만 읽는다.
  큰 섹션 통째 읽기 금지. 표의 단위 행((단위: 백만원) 등)을 반드시 확인한다.
- 판정: 값·단위·기간(당기/전기, 누적/분기)·통화가 모두 맞으면 PASS.

### d. 표현 오류
- report_lint 결과(`range_tilde`, `currency_unit_mix`, `direction_conflict`)를 확인하고, 보고서를 읽으며 추가로 찾는다:
  - 범위 표기: 같은 단락에 `~`가 2개 이상이면 Markdown 취소선으로 렌더되어 "4~5배"가 "45배"로 보인다 → FAIL. 수정 제안은 `4–5배`.
    원문 그대로 "45배", "1.41.7배"처럼 숫자가 붙어 범위가 사라진 곳도 FAIL.
  - 통화·단위 혼합: "USD 3,653억원"류.
  - 증감 방향: 증가/감소, +/-, △ 표기가 숫자의 실제 방향(전기 대비)과 맞는지. 특히 b에서 받은 API 값으로 증감 방향을 검산한다.

### e. "추정:" 누락
- 원문·API에 직접 근거가 없는 해석·전망·인과 주장("~때문으로 보인다", "~할 것이다", "~로 판단된다")이 "추정:" 없이 쓰였는지.
  단, "종합 의견"·"판단" 등 작성자의 의견임이 절 제목이나 문장에 명시된 곳은 PASS로 본다. 경영진 발언을 출처와 함께 옮긴 것도 PASS.

### 리뷰 파일
`reports/<보고서 파일명에서 .md를 뺀 이름>.review.md`에 저장:

```
# 리뷰: <보고서 파일명>
> 리뷰일 <오늘> / 리뷰어: 독립 서브에이전트 / 대상 rcept_no …

## 요약
| 항목 | 결과 | FAIL 수 |
|---|---|---|
| a. 출처 누락 | PASS/FAIL | n |
| b. 재무 표 API 대조 | … | … |
| c. 원문 샘플 5개 | … | … |
| d. 표현 오류 | … | … |
| e. 추정 표기 | … | … |

## a. 출처 누락
(FAIL마다: 위치(절 번호·문장 앞 20자) / 문제 / 수정 제안)
## b. 재무 표 API 대조
(대조한 셀 수, 불일치 표)
## c. 원문 샘플
| # | 위치 | 보고서 값 | 원문 값(단위) | 원문 위치(section_id) | 판정 |
## d. 표현 오류
## e. 추정 표기
## 리뷰어 툴 사용
(MCP 툴별 호출 횟수, 읽은 글자 수 = get_disclosure_section returned_chars 합 + search_in_disclosure context 합)
```

항목 전체가 문제없으면 PASS, 하나라도 FAIL 항목이 있으면 FAIL. 짧게 쓰고, 원문을 길게 옮기지 않는다.
